01

项目究竟解决什么

它是 Agent 与 RL 训练系统之间的连接层，而不是一个重新实现 PPO / GRPO 的通用训练框架。

生产 Agent 通常已经会调用模型、运行工具、处理多轮对话。训练时真正缺少的是：可大规模并行的执行环境、可靠的结果回收，以及与真实采样一致的 token 和 logprob。ART 将这几件事拆开，使业务 Agent 尽可能复用原有代码。

执行层

让 Agent 跑起来

利用 Bedrock AgentCore Runtime（ACR）的会话隔离和路由承载任务；SDK 管理提交、后台执行、结果读取和会话清理。

采集层

让交互能被训练

Rollout Gateway 位于模型请求路径上，负责渲染 token、调用采样后端并记录真实生成 token、logprob 与 loss mask。

训练适配层

让引擎吃得懂数据

verl、Tinker API、slime 各自把通用轨迹转换成自己的训练样本，处理 reward、优势估计、批次形状和更新时序。

最重要的理解：Agent 的最终 JSON 结果与模型的 token 轨迹走不同通道。前者回答“任务做得怎样”，后者回答“模型究竟生成了什么”。训练端把它们按 episode / session 关联，才形成训练样本。

只做评估时，可以直接使用 RolloutClient 收集业务结果，不必经过网关或训练引擎。网关的 TraceRecord 和轨迹核心不依赖 torch；推理和优化器由后端承担。Sandbox SDK 是独立的程序执行能力，也不是每次 rollout 的必经模块。

03

S3 路径：把长任务拆成提交与回收

AgentCoreRLApp 与 RolloutClient / RolloutFuture 是配套的服务端和客户端。

  1. 客户端准备关联信息。

    invoke() 或 invoke_async() 准备 session / input ID，构造 _rollout，携带 exp_id、input_id、s3_bucket 及模型配置。等待本地请求限速后调用 AWS InvokeAgentRuntime。

  2. 服务端先确认接收，不等待 Agent 完成。

    @app.rollout_entrypoint 检查 S3 配置，计算结果键，创建后台任务，立即返回 {status: "processing", s3_bucket, result_key}。若三个 S3 字段出现任一个，就必须全部提供；没有 S3 配置也可后台运行，但这条路径不会回收返回值。

  3. 后台运行原业务函数。

    登记 async task，使健康检查反映 busy；通过上游 _invoke_handler 兼容同步和异步函数，同步逻辑在线程池执行。模型地址、模型名和采样参数由本次 payload 决定。

  4. 写入最终 JSON。

    S3 模式要求返回 JSON 可序列化的 dict。SDK 添加状态及关联元数据；业务异常尝试写入 status_code=500、stop_reason、traceback。无论成功失败，最后解除 async task 登记。

  5. Future 等到对象出现，再取回。

    收到提交确认后，客户端才返回 Future。等待时以 HEAD 检测对象，404 则退避，存在后 GET 并缓存 JSON。成功取回或显式等待超时后尝试停止 Runtime session。

训练端                  AgentCoreRLApp                 S3
  │ invoke(payload) ────────→ │                          │
  │ ← processing + key ───── │                          │
  │                          │ Agent / tools / reward   │
  │ HEAD(key) ─────────────────────────────────────────→│
  │                          │ put_object(result) ─────→│
  │ GET(key) ──────────────────────────────────────────→│
  │ ← 最终 JSON ────────────────────────────────────────│
  │ stop_runtime_session ──→ │                          │

这里真正持久化的是什么

s3://{s3_bucket}/{exp_id}/{input_id}/{session_id}.json

业务 dict 没有统一必填键；例如训练常返回 {"rewards": 1.0}，评估也可返回指标和完整产物。status_code / stop_reason 仅在缺失时补默认值；input_id / s3_bucket / result_key / payload 是 SDK 写入的关联字段，应用应避免占用。

确定性结果键不等于幂等执行。重复提交同一 session 的 S3 rollout 仍会创建新后台任务；结果可能覆盖同一个对象，也可能读取旧对象。不要把这条路径当成 exactly-once 队列。S3 写入及错误结果写入都失败时，客户端只能继续等待或超时。

同步、异步与批量接口怎么选

future.result(timeout=…) 适合同步代码；await future.result_async(timeout=…) 适合异步编排。run_batch / run_batch_async 额外管理在途会话并发和结果聚合。这里的“invoke 立即返回”是无需等待整个 Agent 任务，不是没有网络提交与冷启动等待。

源码：app.py · rollout_entrypoint / save_resultclient.py · invoke / result / run_batch

04

HTTP 路径与统一会话抽象

HTTP 生命周期是与 S3 并列的实现，不是把 S3 轮询换一个名字。

AgentCoreRuntimeApp：可寻址的 start / get

它保留 @app.entrypoint 的普通 HTTP 行为。只有请求带 _agentcore_runtime 信封时，才进入协议逻辑。start / get 是 JSON 中的 operation，仍通过 /invocations 传输，不是新增两个 HTTP 路由。

{
  "prompt": "业务任务字段保持平铺",
  "_agentcore_runtime": {
    "version": 1,
    "operation": "start",
    "invocation_id": "episode-001",
    "background": true
  }
}

服务端剥离信封后，将应用字段交给 handler。新 start 先写 started.json 再执行；后台模式返回 in_progress，前台模式等待结果。完成时先发布持久化结果，再解除 busy 和唤醒等待者。HTTP 等待被取消不会直接取消已启动的工作。

协议状态判定与含义调用者应做什么
in_progress本进程仍持有该 invocation 的执行任务。用同一 session / invocation ID 继续 get。
completed终态记录包含 result 或 error 字符串，二者互斥。检查 error，不能仅根据 HTTP 200 判断业务成功。
interrupted只有开始记录，但没有存活执行任务。按失败或恢复策略处理，不会自动重跑。
not_found记录不存在；未知 get 不会启动工作。核对 ID、会话与存储是否仍保留。

同一 ID 的重复 start 复用已有状态，即使替换 payload 也不会变成新调用。默认记录位于临时目录下的 .agentcore_runtime/<session哈希>/<invocation_id>/；原子文件替换保证记录发布边界，但跨运行环境保留仍需要持久挂载。一 app 进程对应一个 Runtime session，存活任务表按 invocation ID 索引。

AgentCoreHttpClient.invoke() 返回前台结果或后台 InvocationHandle；get_invocation() 可用已知 ID 重建 handle。handle 的等待超时只结束本地等待，裸客户端不会因为取完结果而停止 Runtime 会话。若目标只是忽略信封的普通 App，直接返回的 JSON 可被包装为已完成结果，但不会凭空获得远端恢复能力。

RolloutSession：对训练编排隐藏 transport 差异

setup(task)准备执行环境
→
run(task)返回 RolloutDumpResponse
→
shutdown()收尾与资源清理

统一结果为 task_output、reward、metrics、exception；成功判据要求 exception 为空且 output / reward 不为 None，零奖励仍是有效结果。公共有界生命周期分别控制 container 槽、创建速率、setup 超时和 run 槽，清理仍在 container 槽内执行。

S3 / HTTP

同样生命周期，不同契约

S3 Session 把任务变为 _rollout 调用，读取复数 rewards。HTTP Session 直接提交任务，读取单数 reward，退出时尝试 stop；它的 setup 是空操作。

A2A

两阶段任务协议

首条 message 创建 task 并 setup，等到 input-required；第二条 message 驱动 rollout，再从名为 rollout 的 artifact 读取 dump。AgentCore 与 Docker 各有自己的环境启动和清理实现。

实现边界：make_session() 当前只接受 agentcore_a2a、docker_a2a、agentcore_s3。HTTP Session 已实现，但由 Tinker 直接构造，不在这个 factory 分支中。A2A 的 task/message ID 也不能套用 HTTP invocation 的持久去重保证。

05

模型网关：在采样现场拿到真实 token

它不是在普通 chat 响应里“猜 token”，而是自己掌握模型输入和输出两端的 token 表示。

  1. 协议接入与会话识别。

    OpenAI /v1/chat/completions 和 Anthropic /v1/messages 共用一个 aiohttp App 和 TrajectoryManager。推荐将 sid 放在 Bearer / api-key 中，使用固定 base_url；检查关闭状态、注册白名单与轮数限制。

  2. 归一化消息。

    协议 adapter 将文本、reasoning、tool call/result 转换为共同消息结构。用于协议关联的工具调用 ID 被规范化处理，工具参数保留为 dict，使历史可按消息内容匹配。

  3. 渲染或修复 prompt。

    HfTemplateRenderer 用 HF chat template 渲染文本并编码；linear 模式先恢复已实际服务过的 token 前缀。上下文预算在这里限制可生成长度；prompt 已占满窗口时拒绝调用采样后端。

  4. 调用 token-in / token-out 后端。

    SamplingBackend.generate() 返回 TurnRecord：prompt IDs、output IDs、output logprobs、完成原因等。网关不执行梯度更新，也不执行 Agent 的工具。

  5. 解析回复并记录一轮。

    renderer 将输出解析为文本、reasoning 和工具调用，adapter 组织对应协议响应，然后提交 linear 状态并 record_turn()。任务结束时由编排端 finish_session() 等待在途请求并导出轨迹。

SamplingBackend 是推理引擎差异的主要隔离点
实现下游调用所在位置
SglangHttpBackendSGLang /generate，从输出 token logprob 记录取 token IDs；取消等情况尝试 abort。rollout_gateway/sampling_backends/
VllmHttpBackendvLLM token 级 /inference/v1/generate，并非将 chat 请求原封转发。rollout_gateway/sampling_backends/
TinkerSdkBackendModelInput.from_ints 与 SDK sampling client；权重切换由上层管理。rollout_gateway/sampling_backends/
VerlSamplingBackendverl 内部的 Ray LLMServerClient，复用训练集群推理副本。backends/verl/，而非公共 HTTP 后端目录。

采到的 token 如何从网关进入主训练任务？见第 07 节的进程内轨迹回收与 TransferQueue 交付链路；它与 Agent 的 S3 / HTTP 业务结果通道分开。

工具解析为什么与 tokenizer 绑定

同样是工具调用，不同模型生成的语法不同。默认 renderer 根据 chat template 的 SHA256 查找响应 schema，再调用 tokenizer.parse_response 一次性提取 reasoning、文本和工具。schema 解析失败退回原始文本并标记 ill_formed；注入自定义 reasoning / tool parser 会关闭 schema 自动检测。

未知模板且没有显式 tool parser 时，带工具的请求会在输出解析阶段失败。不能把“支持 OpenAI 协议”理解成“任意模型的工具格式都能解析”。schema 注册表主要来自 TRL，并保留本地模板映射。

服务能力的准确边界

  • 默认未知 sid 会自动开会话；暴露给不可信网络时应启用 require_registered_sessions=True 并控制网络访问。它验证已注册 sid，不是 IAM 身份验证。
  • 支持 SSE 响应包装，但目前先等完整生成结果，再分块发送；不是采样中的逐 token 实时流。
  • 公共 adapter 链路不是完整多模态实现；后端接口预留 image/video 参数，不代表上游已经贯通。
  • 轨迹状态在网关内存中。S3 已有业务结果并不意味着网关重启后还能恢复丢失的 token 轨迹。

06

轨迹：为什么一条任务会变成多行样本

对话历史是结构化消息，训练对象却是精确的 token 序列。这两种表示不总能无损往返。

先理解 TraceRecord 的形状

TurnRecord 表示一次模型采样；TraceRecord 表示交给训练器的一行。token_ids 是全序列，loss_mask / logprobs 只覆盖去掉首轮 prompt 后的 response 区域，它们并非三个等长数组。

示意：P = 首轮 prompt，Y = 模型生成，O = 工具观察

token_ids       [ P P P | Y Y | O O O | Y Y ]
response suffix         [ Y Y | O O O | Y Y ]
loss_mask               [ 1 1 | 0 0 0 | 1 1 ]
logprobs                [ lp1 | 0 0 0 | lp2 ]

len(logprobs) == len(loss_mask) <= len(token_ids)
response_length = response 后缀长度，而不是 sum(loss_mask)

工具观察仍是模型需要读取的上下文，因此保留 token，但不直接贡献训练损失。logprob 的零既可能是 masked 占位，也可能来自后端缺失概率时的补零，不能统一解释为真实的采样概率。TraceRecord 构造器只检查上述长度关系，不替消费者检查所有训练不变量。

tree 模式：消息分叉与 token FORK 是两件事

消息树

决定这一轮接到哪里

按 role 与完整消息 dict 的相等关系寻找挂载点。不同系统提示、修改的历史、并行工具分支可以走到不同叶子。同 sid 下的子 Agent 能成为另一个分支，而不必伪装成父 Agent 的线性对话。

CLEAN / FORK

决定 token 能否拼接

沿叶路径收集时，若新 prompt 精确延伸已有 token 前缀，则 CLEAN 合并；否则结束当前行并 FORK 新行。工具 JSON 空格或 reasoning 的重新序列化，都可能让消息“看起来相同”却不再 token 相同。

拆行不是丢弃失败片段，而是为了保留真实生成时的上下文与输出。共享生成前缀只在首次访问的分支上训练，其他分支把它作为 mask=0 的上下文；客户端带来的外部 assistant 历史不会自动变为本次采样的训练目标。

同一 session 的消息树                 导出训练行
system → user → assistant A ─┬→ tool X → assistant B   trace 1
                            └→ tool Y → assistant C   trace 2

两行可共享 episode reward；共享 A 的生成 token 不应重复计入损失。
即使只有一条消息路径，重分词漂移也可能让它 FORK 成多行。

linear 模式：在生成前修复，而非生成后硬拼

LinearHealer 记住实际喂给模型的 prompt 与实际生成输出，下一轮复用这一 canonical token 前缀，补上 assistant closer 和新增观察。底层仍使用同一个 TrajectoryManager；修复的是下一次采样的输入，不是伪造历史 logprob。

它适合消息只追加、tools schema 不变的串行 Agent。遇到编辑、压缩、分叉或 tools 变化时，有 reset / error / passthrough 三种策略。默认 reset 会重新锚定新线性段，仍可能导出多行；同 sid 的并行子 Agent 不应共享这份线性状态。

三个身份需要上层接好：sid 管网关会话，rollout_id 管同一 episode 的多条记录，group 管同题多次采样。TraceRecord 不会自动把 sid 当成 rollout_id。跨 sid 的子 Agent 归组需要编排层显式关联。

token IDs 如何回到主训练任务

不是由 ACR Agent 打包 token IDs 回传。在仓内网关接入路径中，模型采样时 token 已经被训练侧网关采集。S3 / HTTP 主要回收业务输出与奖励；轨迹通过训练后端自己的数据通道进入训练 batch。

第一段：推理服务返回 token，网关按会话记录

以 verl 为例，网关运行在训练侧 AgentLoopWorker 进程中，由后台线程提供 HTTP 服务；不是部署在 ACR Agent 内，也不一定与主 trainer 同进程。每个 worker 进程共享自己的网关实例。

ACR Agent
  │ messages / tools，api-key 携带 sid
  ▼
训练侧 AgentLoopWorker 内的 Rollout Gateway
  │ Renderer：messages → prompt_ids
  │ VerlSamplingBackend：调用 LLMServerClient.generate()
  ▼
verl 推理服务
  │ output.token_ids + output.log_probs
  ▼
网关 TurnRecord → TrajectoryManager.record_turn(sid, ...)
  └─ 同时将普通文本 / 工具调用回复交给 Agent，供它继续执行

输入 token IDs 来自网关 Renderer；输出 token IDs 来自推理服务真实采样结果，不是将 Agent 最终文本重新分词得到的。网关把每轮的 prompt、生成 token 和 logprob 记在内存中，Agent 无需理解这些训练字段。

第二段：本地取出轨迹，再经 verl 的 TransferQueue 交给训练流程

  1. 用同一 sid 汇合业务结果与轨迹。

    Agent 完成后，AgentLoop 等到 S3 最终结果，再调用 gateway.finish_session(sid, ...)，等待在途请求并导出 list[TraceRecord]。这一步直接访问同 worker 进程中的网关对象，不是向 ACR 下载 token，也不是从 S3 读取 token。

  2. 返回 verl 的样本对象。

    _record_to_output() 将每条记录转换为 AgentLoopOutput，携带 prompt_ids、response_ids、response_mask、response_logprobs、reward_score。AgentCoreAgentLoop.run() 返回这个列表；发生轨迹分叉时，一个 episode 可返回多条。

  3. 由 verl worker 写入训练数据通道。

    当前 verl v1 的 AgentLoopWorkerTQ._agent_loop_postprocess() 将 token 转成 torch.int64 张量，拼接 input_ids，补充位置、mask 和奖励等字段，再调用 tq.async_kv_batch_put(...) 写入 TransferQueue。后续 trainer 按 batch key 编排，训练流程从队列读取所需数据。

Agent 最终结果 ── S3 ──→ AgentCoreAgentLoop
                               │
同进程网关内存 ─ finish_session(sid) ─→ list[TraceRecord]
                                         │ _record_to_output()

因此，“网关到 AgentLoop”是进程内对象访问；“rollout worker 到主训练流程”则通过 verl 的 TransferQueue 完成。队列中的任务 / 采样分组 key 由 verl 管理，不应与 ACR 的 sid 混为一谈。

关联的前提是：训练端先注册 sid，再把它作为 api-key 传给 Agent 的模型客户端。若 Agent 绕过网关直接请求模型，或使用错误的 sid，业务结果可能正常返回，但对应会话未必有可训练轨迹。网关内存丢失也不能仅靠 S3 业务结果重建原始采样 token 与 logprob。

仓内源码：worker 进程内网关推理 token 返回record_turnfinish_session / _record_to_output。队列后处理位于已安装的 verl 依赖 verl/trainer/ppo/v1/agent_loop_tq.py，不是本仓库另行实现的 token 上传服务。

7.1 verl：保留完整轨迹，同时稳定优化步数

PayloadDataset 保留真实任务 payload，并适配 verl 所需的 prompt 结构。AgentCoreAgentLoop 为每次尝试创建 session，将同一 ID 用作 Runtime session 与网关 api-key。Agent 通过网关调用训练集群的采样副本；S3 结果到达后，每条 TraceRecord 转成 AgentLoopOutput。

奖励由 Agent 提供，转成 reward_score / rm_scores。可训练 token 最多的一行被放到该 session 的末尾，以配合 verl v1 的 session 级组相对优势计算与广播。随后 old/ref logprob、配置的 rollout correction、actor 更新及权重同步由 verl 执行；这里不是重复实现一套训练器。

难点是任务数固定，导出的轨迹行数却可变。若沿用固定行数 mini-batch，分叉越多就可能多做 optimizer step，改变原先配置的学习节奏。仓内 batching mixin 固定每次更新的分区数量，让每个分区的行数浮动：

K = train_batch_size / parameter_sync_step / ppo_mini_batch_size
补齐行数：只需满足 DP × K 的整除条件。
归一化尺度：保留配置的 ppo_mini_batch_size × rollout.n。

这一实现要求 verl v1、actor-only、无蒸馏以及 seq-mean-token-sum。它稳定优化步数和预设归一化尺度，但不等于每个长短不同的 episode 都有等量 token 损失权重。初始 prompt 超出存储分区时，溢出部分移到 response 区并置 mask=0，而不是简单丢弃。

失败处理区分模型上下文耗尽、普通 Agent 错误、瞬时基础设施异常和超时。瞬时错误可在共享总期限内换新 session 重试；有轨迹的模型限制失败可零奖训练。普通 Agent 错误和超时默认丢弃，部分策略可配置；同步 trainer 还有连续高丢弃率保护。

7.2 Tinker API：CPU 编排、同步组相对更新

  1. 每题采一组 episode。

    读取平铺 JSONL 任务，注入 _config={base_url, model_id, api_key}，用 HTTP Session 后台执行。Agent 返回单数 reward；成功响应要求有限数值，拒绝 bool、字符串和缺失值。

  2. 按 episode 计算优势，不按 trace 行计数。

    同题可评分 episode 的奖励求均值，A = reward − mean(group rewards)，不除标准差。有效 episode 少于两个或组内奖励完全相同，则不生成该组的训练数据。

  3. 构建 next-token Datum。

    token 序列错一位对齐输入与目标；prompt、工具上下文及共享前缀的位置不贡献 advantage。一个 episode 分成多行时仍共享该 episode 的优势。

  4. 完整收批后更新，再切换采样模型。

    调用 forward_backward_async(loss_fn="importance_sampling") 和 Adam 更新，消费结果后保存权重并替换 sampling client，下一批才开始。这条 recipe 没有实现 clipped PPO 或显式 KL 项。

调用失败但已有可训练 token 时可零奖保留；无 token 的 episode 不计入奖励统计。验证在训练前、按间隔及结束时运行，每题单次采样，不构建训练 datum，增量写 JSONL 并报告覆盖、失败和截断情况。当前入口可保存 checkpoint，但未提供恢复训练参数。

7.3 两条 slime 路径必须分开看

experimental/slime

逐样本生成 hook

进程单例维护仓内 RolloutGateway、后台线程与 RolloutClient。一次 generate 调用提交一个 metadata.payload，完成后将轨迹映射为多个 slime Sample。

奖励归一化按 group_index 分组，按 rollout_id 去重，防止分叉多的 episode 重复影响组均值。缺失奖励交回 slime 后续 reward 路径处理。

调用失败并不总是 ABORTED：已有可用轨迹时可零奖保留；无有效记录才用 ABORTED + remove_sample=True 排除。

backends/slime

整批 rollout hook

当前仍启动外部 rllm_model_gateway 子进程；不是仓内新网关。按 session URL 路由，将整个 metadata 作为 Agent 输入，整批收集并转换轨迹。

相邻 token 前缀精确延伸才合并，否则切段；工具桥接内容 mask=0。按任务与 gateway session 归一化，并处理 DP 补齐行。

训练侧调用或转换抛出异常、或轨迹为空时，产生零梯度 FAILED 占位，其零奖励仍会进入组基线。但当前未检查 S3 的 Agent 错误状态；Agent 报错前已生成的轨迹，仍可能按零奖励参与训练。

两者都有接入代码，目录名不是“已废弃”或“已验证”的证据。GPU 训练环境和 slime / Megatron 仍需独立准备；具体命令、模型和 CUDA 约束应查各自 setup，而非混用。

Sandbox 与基础设施支撑

RuntimeApp 执行 Python handler；Sandbox 执行任意镜像中的程序。二者共享生命周期思路，但不是同一个实现。

Python Sandbox SDK + Go sandboxd

SandboxClient 管理会话，Sandbox.exec(argv) 通过 Runtime 把命令交给 Go daemon。默认直接执行 argv，不自动套 shell；需要 shell 语法时由调用者显式选择。Sandbox 不负责模型采样和奖励，但可以被 Agent 的 bash 工具或任务 verifier 调用。

  • 同一 invocation ID 的 start 复用旧状态，替换命令不会重复执行；get 只查询。前台 HTTP 断开只结束等待，不接管或销毁进程。
  • 正常完成需要进程退出和输出 EOF；子进程若仍持有输出管道，也会延长等待。stdout / stderr 各保留前 256 KiB，超限仍继续排空并标记截断。
  • 非零退出码是 ExecResult 中的数据；执行 timeout 则持久化结果并在 SDK 抛出 ExecTimeoutError。
  • 执行 timeout 仅杀直接进程，不保证终结所有后代；ExecHandle.result(timeout=…) 则只限制本地等待，不停止远端工作。
  • 恢复依赖记录存储仍然存在。默认临时目录不是永久存储，停止或替换运行环境后不能无条件恢复。

关键契约与失败边界

接入时最常见的问题不是类名没找对，而是把不同层的“成功”“完成”“超时”当成同一件事。

身份与字段速查

字段语义使用边界
session_id / runtimeSessionId路由到 Runtime 会话。新网关消费者常复用它作为 Bearer sid，但两者语义不同。
invocation_idHTTP / Sandbox 会话内的一次可查询调用。同 ID 复用记录；不是输入数据集的 ID。
input_id / group_index输入或同题多次采样的分组身份。一组可有多个 episode；不要按导出行数计算组样本数。
rollout_id将同一 episode 的多条 TraceRecord 归在一起。由编排方赋值，不自动发现跨 sid 的子 Agent。
_rolloutS3 路径的结果位置与模型运行配置。不是 HTTP 生命周期信封；不要与 _config 混用。
rewards / reward前者用于这里的 S3 训练接入，后者用于 Tinker HTTP。App 本身允许任意 JSON dict；严格程度由消费后端决定。

奖励解析不是全仓统一规则

verl 的 built-in reward 接受标量或列表末项，缺失时记零，无法转换时报错；experimental/slime 缺失时交由 slime 评分；Tinker 要求有限数值且拒绝 bool / 字符串。RewardFunction 是计算接口，不会替所有 transport 和后端统一奖励契约。迁移 Agent 时要同时核对输入布局、输出字段与后端校验。

“返回成功”可能只代表任务已接收

S3 的 processing 响应不是最终业务成功。HTTP 的 completed 也可能包含 error，interrupted / not_found 同样可能是 HTTP 200。应在正确层检查状态：传输状态、执行状态、业务奖励、可训练轨迹各是一层。

超时和清理必须按调用路径理解

S3 Future 成功回收和显式等待超时会尝试 stop，但任意 HEAD/GET 异常、外部取消、提交失败或提前退出迭代，不能概括成“都自动清理”。HTTP handle 等待超时不取消执行；HTTP Session 上下文才负责收尾。stop 是 best-effort，调用过并不证明远端已释放。

网关截断与训练失败不是同一个状态机

上下文预算可能在生成前拒绝请求，后端也可能返回 length 完成原因。导出记录还可被长度上限裁切；不能只看 TraceRecord.status 就判断所有截断。各训练后端结合上下文耗尽标记、错误原因和已有 token 决定零奖保留还是丢弃。

真实可达性与模型一致性仍是部署前提

ACR 内的 Agent 必须能访问训练侧网关；base_url 应符合所用 SDK 的路径规则。网关 tokenizer / chat template 必须与采样模型一致，模型工具语法必须有解析支持。单元测试中的 fake backend 不能替代这几项部署验证。

一条数学任务走完全程

以仓库的 Strands 数学 Agent 与 verl / S3 接入为例。以下是链路说明，不是本次实际启动的训练。

  1. 训练器取出题目与标准答案。

    数据 payload 提供 prompt、answer。同题可采多次，分组身份用于后续组相对优势计算，每次 episode 使用独立 session。

  2. 训练侧先准备模型调用路径。

    注册网关 session 并传入采样默认值，再用 RolloutClient 将 base_url、model_id、api_key 连同 S3 关联配置放进 _rollout。

  3. ACR 接收后，rl_app 在后台运行。

    入口从 _rollout 构建 OpenAIModel，每次创建 Strands Agent。模型和 Agent 不共享跨 rollout 的对话状态；此示例使用 NullConversationManager。

  4. 模型请求经过网关，工具在 Agent 侧执行。

    Agent 先请求模型；网关捕获 token 并返回 calculator 工具调用；Strands 执行 calculator，把结果放回历史再请求模型。网关记录新一轮生成，工具结果作为 mask=0 的上下文。

  5. 业务奖励走 S3，token 轨迹留在网关。

    Agent 拼接最终文本块，调用 GSM8KReward 对照标准答案，返回 {"rewards": …}。App 保存 JSON；Future 获取结果后尝试 stop Runtime。

  6. 训练端汇合并更新。

    导出该 session 的 TraceRecord，附 episode 奖励，转换成 verl 输出；按组计算优势并训练生成位置。工具观察影响后续预测，但不作为模型生成目标反向优化。

扩展时把改动放在哪一层

新 Agent 框架：优先复用原生模型客户端，适配业务入口与奖励。新的通信协议：扩展 adapter。新模型格式：扩展 renderer / schema / parser。新推理引擎：实现 SamplingBackend。新运行环境：实现 RolloutSession 生命周期。新训练器：在后端转换 TraceRecord，而不是让网关依赖训练器张量类型。
